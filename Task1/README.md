# Задание 1. Повышение безопасности системы

Схема решения - `BionicPRO_C4_to-be.drawio`. Приложение для донастройки протеза теперь ходит в API не напрямую, а через Auth BFF.

### Что не так сейчас

SSO сделан на Authorization Code Grant в Keycloak, но код и токены можно увести.

- Клиент `reports-frontend` публичный, PKCE не включен. Перехваченный код авторизации можно обменять на токен, сервер не проверяет, что это делает тот же клиент, который начинал вход.
- Токен живет в браузере. Фронтенд берет `keycloak.token` и сам кладет его в заголовок `Authorization`, и получается что токен доступен любому скрипту на странице.
- У клиента включен Direct Access Grant, логин и пароль можно отправить в Keycloak напрямую, без страницы входа.
- Пользователи с паролями хранятся в самом Keycloak, одной базой на все страны. При выходе на новые рынки это будет блокером.

### Что добавляется

| Элемент | Зачем |
|---|---|
| Веб-приложение отчетов | Интерфейс для юзеров. Токенов не получает, работает по HTTP-only cookie |
| Auth BFF | Свой API между фронтендом и остальной системой. Проходит вход через Keycloak, хранит токены у себя на сервере, обновляет их и ходит с ними в API |
| Keycloak | Единый вход (SSO) для всех приложений BionicPRO и роли пользователей |
| Keycloak DB (PostgreSQL) | Настройки realm, клиенты и роли |
| LDAP представительств (внешние) | Учетные записи пользователей. В каждой стране свой каталог |
| Внешние IdP стран (внешние) | Вход через поставщиков удостоверений других стран |

### Как проходит вход

1. Юзер открывает приложение, его перенаправляют на страницу входа Keycloak.
2. Auth BFF перед этим генерирует `state` и `code_verifier`, а в Keycloak отправляет хеш от `code_verifier`.
3. Юзер вводит логин и пароль. Keycloak проверяет их в LDAP его страны. Если юзер выбрал вход через IdP своей страны, Keycloak перенаправляет его туда и просто получает обратно подтверждение.
4. Keycloak возвращает пользователя с кодом авторизации. Auth BFF сверяет `state` и меняет код вместе с `code_verifier` на токены. Перехваченный код без `code_verifier` ничего не дает.
5. Токены остаются в Auth BFF. Браузеру отдается только HTTP-only cookie сессии.
6. Дальше фронтенд ходит в Auth BFF с этой cookie, а Auth BFF идет в API с access token. API проверяет подпись JWT публичным ключом Keycloak, который берет из `.well-known/openid-configuration`, и смотрит роль пользователя.

### Работа с токенами

Access token короткий, 5 минут (`expires_in: 300`). Если его украдут, злоумышленник успеет немного. Когда он истекает, Auth BFF сам получает новый по refresh token, пользователь заново не логинится. Refresh token живет 30 минут (`refresh_expires_in: 1800`) и тоже не покидает Auth BFF.

Мобильное приложение работает так же, через Auth BFF.

### Хранение учетных данных в странах

Учетные записи хранятся не в Keycloak, а в LDAP представительства каждой страны. Каталог стоит в этой стране и подчиняется ее законам. Keycloak подключает каталоги через User Federation, на каждую страну свой LDAP-провайдер, и только проверяет логин и пароль. Новая страна подключается просто добавлением еще одного провайдера.

### Вход через внешние IdP

Если в стране есть свой поставщик удостоверений, Keycloak подключает его по схеме Federated Identity. Пользователь логинится во внешнем IdP, тот возвращает в Keycloak подписанное утверждение, а Keycloak маппит его роли или группы на роли BionicPRO.

### Что меняется в настройках Keycloak

- Для клиентов включается PKCE.
- Direct Access Grant выключается.
- Вместо публичного клиента для фронтенда заводится клиент для Auth BFF с секретом, секрет хранится в Auth BFF, а не во фронтенде.
